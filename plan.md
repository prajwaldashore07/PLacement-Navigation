# MITS Placement Navigation Platform — Implementation Plan

## Scope and architecture

Deliver the full requested student placement platform as a vanilla HTML/CSS/JavaScript client served by Node.js/Express, with REST/JSON endpoints and managed MySQL. Keep the client framework-free and make each feature page a module that uses a shared API client, session state and reusable UI patterns. The server is separated into routes, controllers, services/domain logic, middleware, validators and parameterized SQL repositories. Database schema, repeatable seed/import scripts and migrations are maintained independently from process startup. Student and admin functionality is protected by server-validated sessions and roles; admin passwords are hashed and configured through environment variables. The requested enrollment-number-only student flow is implemented only as clearly labeled fictional/demo access, not represented as secure real-world authentication.

The server owns eligibility decisions, application validation, test scoring, student ownership checks, role authorization and file metadata. Student academic criteria come from official records, not browser state. Opportunities and test content are demonstration data unless verified. Applications are platform tracker records, not employer submissions. Resumes are size/type checked on both sides, privately uploaded to durable project storage through server-authorized storage requests, and associated with an authenticated student in MySQL. The runtime storage API supports hiding a resume record but not physical object deletion; this limit is disclosed and physical erasure is reserved for an authorized storage-operator path. MySQL is shared by development and publication, so migrations are additive and seeds are idempotent/non-destructive.

## Build sequence

1. Inspect the initialized workspace and runtime/config declarations; establish project structure, diagnostics, dependency policy, and route manifest before starting the server.
2. Implement database schema/migrations and idempotent seed generation for at least 200 fictional students, 20+ fictional roles, and varied question/roadmap content; keep startup separate from one-time migration and seed work.
3. Implement server foundations (configuration, pool, middleware, sessions, role checks, validation, error handling and REST routing), then student onboarding, profile, private resume, eligibility, applications, mock tests, learning, and protected admin services.
4. Build the design system and responsive vanilla client, implementing the ordered login/interests/skills/resume/profile-summary/dashboard flow and all remaining student/admin pages against live APIs.
5. Add focused automated tests for eligibility precedence/reasons, scoring, validation, authorization, duplicate applications and data ownership; run code diagnostics and actual HTTP/API checks. Avoid destructive test writes to the managed database.
6. Complete README, `.env.example`, migration/deployment instructions, platform logo metadata and final route manifest. Document real deployment configuration still needed (for example admin bootstrap secret, external employer integration and any storage-operator deletion path).

## Project structure

- `client/app.js` — history routing, session-aware access guards and route rendering; `client/api.js` — same-origin Fetch/XHR and CSRF handling.
- `client/views/` — enrollment, onboarding, student dashboard, company explorer/details, applications, mock tests/results, learning, profile and administration pages.
- `client/components/` and `client/styles/` — shared navigation, dialogs, toast/status/form patterns, responsive design tokens and layouts.
- `server/app.js` and `server/index.js` — Express middleware/static hosting, public health/route-manifest endpoints and runtime initialization; `server/routes/` — REST endpoints grouped by authentication, student, company, applications, tests, learning and admin.
- `server/services/` — eligibility calculation, opportunity loading and test scoring; `server/middleware/` — database-backed sessions, CSRF/role protection, input/error handling and rate limiting; `server/db/pool.js` — managed MySQL pool and transaction helper.
- `database/schema.sql`, `database/migrations/`, `database/migrate.js` and `database/seed.js` — normalized schema, versioned additive migrations and repeatable fictional records, including official academic facts, formal per-opportunity rules, opportunity-to-test recommendations and topic-to-mini-quiz links. `database/seed-admin.js` separately hashes the administrator bootstrap password supplied in the environment.
- Resume bytes are held in memory during validation and sent to private managed object storage; only owner-bound metadata is persisted in MySQL. No public resume URLs or local/container persistence are used.
- `tests/` — automated eligibility, scoring and validation tests; `public/` — entry HTML, route manifest and brand mark; root files — pinned pnpm configuration, `package.json`, `.env.example`, `README.md`, `.gitignore`, project metadata and `Dockerfile`.
- Root — package manifest and pinned package manager, `.env.example`, `README.md`, `TODO.md`, `plan.md`, `.gitignore`, and deployment files.

## Design system

Use the user-specified direction: a polished, restrained navy/indigo academic SaaS interface with white surfaces, cool neutral backgrounds and concise blue accents. The design movement is **precision-oriented institutional SaaS**. Core principles: academic information is legible at a glance; evidence and eligibility explanations are transparent; student actions are focused and sequential; the same component patterns work across desktop and mobile. Color communicates trust and hierarchy: deep navy anchors navigation and headings, a distinctive cobalt/indigo identifies active actions, and muted semantic colors are reserved for status and feedback. Layout uses a persistent desktop rail paired with a generous, left-aligned content canvas, compact page headers and flexible data layouts; on mobile the rail becomes a touch-friendly drawer and dense tables become stacked cards. Signature motifs are a slim indigo progress rule, restrained rounded status pills, and crisp academic-data panels with thin borders and subtle shadows.

Interactions should be immediate and calm: visible focus, explicit loading/disabled states, undo/review where consequential, short transitions, and clear explanations. Avoid decorative animation; use 120–200 ms opacity/position transitions and honor reduced-motion preferences. Typography pairs a neutral UI sans (system stack) with a compact tabular-number treatment for CGPA, package, and progress; sizes follow a small consistent hierarchy. Brand essence: **a transparent placement-navigation workspace for MITS engineering students that connects eligibility, preparation and applications**; personality: dependable, focused, encouraging. Voice is direct and specific, e.g. “Two criteria match. One skill needs work.” and “Your application is recorded here—not sent to the employer.” Wordmark concept: a custom simple monogram combining an open book/route line with an ascending placement marker, paired with the platform name; no emoji. Signature brand color: cobalt-indigo `#3347B8`.

## Runtime and dependencies

Use small, maintained Node dependencies only where they support real functionality (Express, MySQL driver, session persistence, password hashing, upload parsing, security headers/rate limiting and test runner). Runtime and secret values come from environment variables; never commit credentials. Serve browser-facing API requests with relative paths. Set session cookies for cross-site HTTPS Preview to `SameSite=None; Secure`; keep ordinary local HTTP configuration explicitly separate rather than inferring from `req.secure`/`NODE_ENV`. The HTML site and REST API are served together by Express, with additive migrations and idempotent seed data, `/health` unauthenticated, and `/manus-routes.json` served as a real static JSON asset.
